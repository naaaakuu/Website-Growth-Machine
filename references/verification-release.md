# Verification and Release

Load before claiming test completion, release readiness, deployment, monitoring, or post-launch results.

## Evidence rules

Set acceptance criteria before implementation. For every result record criterion, scope, URL/journey/state, environment, build/commit, tool/version/configuration, timestamp, raw evidence path, observation, limitation, reviewer, and approval. Retain failed and unfavorable runs. Revalidate evidence after material changes.

Use PASS only for a scoped criterion met by recorded evidence; FAIL for a scoped test that did not meet it; NOT_TESTED for absent adequate evidence; BLOCKED for a specific missing tool/permission/decision; and N/A only with a reason.

## Gate families

Decide applicable scope for objective/offer, approvals/protected assets, functional journeys, search access, content/claims, accessibility, lab performance, field observation, measurement, reliability/security, migration, and release/operations. Never average gates. A strong lab score does not offset a broken form, unavailable site, duplicate revenue, fabricated claim, or inaccessible journey.

## Release workflow

Before an approved production release, review exact changes, scope, protected-asset diffs, migration map, required reviews, evidence, known risks, rollback, monitoring owner, and approval. After release, run safe public smoke checks and authorized test events. Verify production crawl controls, assets, and route behavior; distinguish a preview from deployed production.

Observe outcomes only over an appropriate window/cohort. Field data, indexing, seasonality, and sales cycles differ. Do not force a seven- or thirty-day result.
